# Write-up

## Schema reasoning

The relationship chain `organizations → org_members → workflows → workflow_steps/workflow_triggers`, and `workflows → workflow_runs → step_runs`, matches how the two permission layers need to query it: every permission check on a workflow-family table walks up through `organization.members` to find the caller's role, so that relationship has to exist as a real FK, not be inferred at query time. `step_runs` is deliberately separate from `workflow_steps` (a step definition vs. one execution of it) so the same step can run — and fail, retry, and get approved — many times across many runs without mutating the definition. `workflow_step_outputs` is a dedicated table (rather than writing `db_write` results back into `step_runs.output`) because the assignment asks for `db_write` to save results "into your own tables" — a real destination table, org-scoped, that a `db_write` step's Layer 2a gating and Layer 1 select permissions both apply to independently of `step_runs`. `notifications` and `trigger_events` exist because `notify` and the database-event trigger are both explicitly required to be Event-Trigger-based rather than inline function calls — the engine writes a row, and a Hasura Event Trigger is what actually does the work, so those tables are the interface between the two, not incidental logging. `org_usage_current_period` is a view rather than a materialized/cached table because usage should never be stale mid-conversation with the quota indicator; `organizations.quota_used` stays a plain incrementable column because the Action handler needs a single atomic check-then-increment, which a view aggregating across runs doesn't cleanly give you.

Org/workflow creation is intentionally **not** self-serve via a Hasura permission — an editor can create a workflow because they're already a member of an org, but nothing can insert the *first* `org_members` row for a new org without already being a member (a real chicken-and-egg that most systems solve with an invite flow or an admin step). Rather than build an invite system as a false requirement, org creation and initial ownership assignment happen via the admin secret (seeding), which is realistic and keeps the permission model honest about what it's actually protecting.

## The two permission layers, enforced differently

**Layer 1 (org + role scoping)** is plain Hasura row-level permissions. Every table's `select`/`insert`/`update`/`delete` permission filters through `organization.members.user_id = X-Hasura-User-Id`, so an editor in Org A structurally cannot see Org B's rows — not because of an application check that might be forgotten somewhere, but because Hasura never returns or accepts a row outside that filter, including on a direct primary-key lookup by guessed ID (`workflows_by_pk` returns `null`, not a 403 — the row doesn't exist as far as that caller's query is concerned).

**Layer 2 is two different mechanisms**, because it's two different kinds of decision:

- *Layer 2a — still declarative, but content-aware.* Whether an insert into `workflow_steps` is allowed depends on the row's own `type` column: `db_write`/`notify` require `owner`, everything else allows `owner` or `editor`. This is expressed as a Hasura insert/update **check expression** — an `_or` of two branches, one gated by type + owner, one by type + owner-or-editor. Same table can be tracked by the same Hasura permission system as Layer 1, it's just a richer boolean expression than "is a member." `workflow_triggers` gets the identical treatment for `webhook`-type triggers.
- *Layer 2b — genuinely can't be a row permission.* Approving a paused `approval_gate` step isn't an insert or update of a row the caller owns in any declarative sense — it's "resume this specific in-flight process," a decision that depends on the *current state of a multi-step execution*, not on the shape of one row. `functions/approveStep.ts` checks the caller's org role in code (`getOrgRole` query, then an explicit `if (role !== 'owner' && role !== 'editor') return 403`) before calling back into the engine. This is the same reason `triggerWorkflowRun.ts` also checks role and quota in code rather than relying solely on the Action's Hasura-level permission (which only gates *who can call the Action at all*, not the business logic inside it) — the assignment is explicit that this check belongs in the handler, and testing confirms it: a viewer or a cross-org user hitting `approveStep` with a guessed `step_run_id` gets a 403 from the handler, independent of whether Hasura would have let the read through.

## Approval-gate pause/resume

The engine (`functions/_lib/workflowEngine.ts`) runs steps in a plain sequential loop, updating `step_runs`/`workflow_runs` as it goes so the subscription reflects progress live. Hitting an `approval_gate` step sets that step to `awaiting_approval`, sets `workflow_runs.status = 'paused'`, and **returns** — the loop simply stops; there's no polling or waiting thread. `approveStep` later re-enters the *same* engine via `resumeEngineRun`, which re-fetches the ordered step list, maps existing `step_runs` back onto it by `workflow_step_id` (so it doesn't recreate rows), computes the step index to resume from (`approval_gate`'s `step_order + 1`), and calls the identical loop function with that starting index. Two separate serverless invocations, same engine code, same table as the hand-off point — the pause is just "stop appending to this run," and resume is "start appending again from a specific index," which is why the fix for the quota bug found during testing (usage counted per-call immediately rather than batched at the end) mattered: anything that only happens "at the end" of `runLoop()` silently doesn't happen for a run that pauses, because a paused run's "end" is actually the start of a second, separate invocation.
